贴吧一键签到:两套签名、两个接口,和一个被我弄丢的任务 ⏰

📖 约 10 分钟 · #Python #逆向 #Windows #自动化

想要的东西很简单:每天早上,自动把关注的贴吧签到一遍,不用掏出手机点二十次。 真正花时间的不是签到本身,而是它背后那两个接口——一个校验签名、一个不校验, 错误码却长得几乎一样。中途我还在没权限的窗口里跑了一次安装脚本, 把已经装好的计划任务删了个干净。

一、需求十分钟,边角两小时

需求能一句话说完:用 cookie 登录,取出关注列表,逐个签到,失败重试,能无人值守。 我一开始以为就是这样一个 Python 文件的事,最后它长成了两千多行、13 个文件: 主脚本、自测、四个 PowerShell 脚本、一个批处理引导,还有 README。

多出来的东西几乎全在边角上:

  • 网络有时候连不上,得自己换一条路;
  • 接口有两套,签名算法也有两套,还不能混用;
  • Windows 控制台的编码会把中文日志搅成乱码;
  • 计划任务的「开机触发」有一种静默失效的姿势。

代码是开源的,贴在 GitHub 上:Hare-Athena-III/tieba-signin。下面只讲思路和踩过的坑,不逐行讲实现。

二、翻车一:requests 连不上,urllib 却行

第一版写完,一次都没成功过。报的错很单调: 

ReadTimeout: HTTPSConnectionPool(host='tieba.baidu.com', port=443):
Read timed out. (read timeout=8.0)

稳定超时,重试也没用。但同一台机器、同一个时刻,拿标准库发一个请求,却是正常的 HTTP 200: 

import urllib.request, requests

# 标准库:200
urllib.request.urlopen("https://tieba.baidu.com/f?kw=test", timeout=8).status

# requests:稳定 ReadTimeout
requests.get("https://tieba.baidu.com/f?kw=test", timeout=8)

这就排除了「贴吧挂了」「网络不通」「cookie 错了」——问题出在请求库这一层。 这台机器上代理软件在 7897 端口开着,但注意:脚本默认是直连的, 直连也通。所以不是代理配置的问题,而是 requests 在这台机器上 tieba.baidu.com 走不通(TLS 握手或 HTTP 实现上的差异)。

我没有继续往底层挖,而是把它当成一个环境差异来处理:

  • 先试 requests:API 顺手、异常清晰、超时可控;
  • 失败(超时 / 连接错误)就自动切到标准库 urllib,用同一套请求构造和解析逻辑;
  • --transport requests|urllib|auto 可以手动指定,想看看到底走哪条路就写日志。

这不是最优雅的解法,但是个诚实的解法:能用哪条路就用哪条路,并且让日志说清楚用了哪条。 后来跑真实签到,日志里那行 HTTP 后端:自动选中 urllib 就是它自己选的。

三、两个接口,两套签名

贴吧有两套签到入口,行为差别很大:

  • 移动端:c.tieba.baidu.com/c/c/forum/sign, 返回里有本吧排名,但要传签名;
  • Web:/sign/add,参数简单,不传签名也能用。

两种签名算法:

# 移动端:单层 md5,值不做 URL 编码
def sign_mobile(kw, tbs):
    return md5(f"kw={kw}tbs={tbs}tiebaclient!!!".encode()).hexdigest()

# Web:两层 md5,里层对「排好序的 k=v」做摘要,值是 encodeURIComponent 过的
def sign_web(params):
    body = "&".join(
        f"{k}={quote(str(v), safe='')}"   # 关键:safe=''
        for k, v in sorted(params.items())
    )
    inner = md5(body.encode()).hexdigest()
    return md5((inner + "tiebaclient!!!").encode()).hexdigest()

最容易错的是那个 safe=''。Python 的 quote 默认是 safe='/',也就是不会编码斜杠;而签名对应的是 JS 的 encodeURIComponent,它会编码斜杠。 参数里只要出现一个 /,签名就悄悄错了 —— 不报错,只是服务端说「签名不对」。

为了确认 quote(safe='') 真的和 JS 一致,我拿 Node 的 crypto 逐位对拍过一遍,不是靠感觉。

四、用错误码当尺子:Web 到底校不校验签名

有个流传很广的说法:Web 签到接口不校验签名。想验证这件事, 按理说得有真实账号,但可以用一个更干净的办法—— 拿一个格式合法、但肯定无效的 BDUSS 去打接口,看错误码。

逻辑是这样:如果签名这一关过了,服务端会往下走到「查登录态」,于是返回 A 类错误;签名被拒,则返回 B 类错误。两者的错误码不会一样。

签名Web /sign/add移动端 forum/sign
算对no=1990055error_code=1
算错 / 不传no=1990055(一模一样)error_code=110001

结论很清楚:Web 接口根本不看签名——算对算错,返回的都是同一个码; 而移动端会校验签名(110001 只在签名错时出现), 并且 tbs 确实参与签名。

那两个「算对」的返回值需要解释一下:1990055 是「账号未实名,不能签到」, error_code=1 是「签名过了,但登录态无效」。它们都不是成功码, 但恰好证明了请求已经走到业务层,而不是被签名关卡拦住。

这个方法的好处是:不需要真实账号,也能给接口行为定性。 整条签到策略就是据此定的——默认走移动端拿排名,签名被拒时自动退回 Web, 而不是把 110001 误当成「登录失效」直接罢手。

顺便把返回码分了个类:

  • 0:签到成功;
  • 1101 / 160002:今天已经签过,也算成功(脚本是幂等的);
  • 1103 / 1104:太快了,等 4~6 秒重试一次;
  • 1 / 2 / 4 / 5 / 7 / 10 / 340006:登录失效,立刻中止,不空跑;
  • 1990055:账号未实名——别折腾 cookie 了,去实名。

五、编码:三分之二的坑都在这里

中文日志进了文件是乱码。原因不复杂,但涉及三方,任何一方不一致就坏:

  • Windows 控制台默认是 GBK(代码页 936);
  • Python 输出要显式 -X utf8;
  • PowerShell 这边要同时设 $OutputEncoding 和 [Console]::OutputEncoding。
$utf8 = New-Object System.Text.UTF8Encoding($false)
$OutputEncoding = $utf8
[Console]::OutputEncoding = $utf8

还有一个更阴的:PowerShell 5.1 读 .ps1 文件时按 系统 ANSI 代码页解码,不带 BOM 的 UTF-8 中文会被读成乱码。 我的 status-task.ps1 就因此报过这种错: 

表达式或语句中包含意外的标记“code，”。
所在位置 ...\status-task.ps1:37 字符: 1

它把紧贴在参数名后面的中文逗号当成了变量名的一部分 —— $code, 于是被解析成 ${code，}。 而失败方式更气人:脚本静默以退出码 0 结束,什么都不输出, 看起来像「跑完了、没东西可显示」。修法只有一个 —— 所有 .ps1 存成 UTF-8 带 BOM,并且写了个小脚本专门检查这件事。

六、无人值守:开机触发为什么会静默失效

定时到点跑已经验证没问题了,但「开机自动签到」怎么都不动。 症状非常有迷惑性:任务列得出来、状态 Ready、触发器显示已启用, 结果开机之后「上次运行时间」一点都没变——它压根没启动过。

原因在运行身份。用当前用户(LogonType=Interactive)注册时, Task Scheduler 只在该用户已经登录的情况下才肯启动任务。 而开机那一刻还没有任何用户登录,于是这次触发被直接跳过,连失败记录都不留。

改成不需要用户会话的身份就好了:

New-ScheduledTaskPrincipal -UserId 'SYSTEM' `
    -LogonType ServiceAccount -RunLevel Highest

换成 SYSTEM 之后有个连带问题:SYSTEM 的 PATH 是机器级 PATH, 看不到用户 PATH 里的 Python。所以注册时必须把解释器解析成绝对路径再写进去, 否则任务跑起来第一句就是「找不到 python」。

另一个问题是「开机时网络还没好」。Windows 没有「网络就绪」触发器, 只能先触发、再自己等。等待方式也换过三次:

判定方式问题
看网卡状态冷启动时早就显示「已连接」,但 DNS 还没通,一跑就超时
解析 DNSWindows PowerShell 5.1 上 Resolve-DnsName 没有 -AsJob,同步调用会一直卡住
ping 域名通 = DNS 和路由都正常,最理想;但有些网络封 ICMP,永远 ping 不通
TCP 连 443ICMP 被封时作为兜底;两者任一通就开始签到

所以现在是 ping 为主、TCP 兜底,每 5 秒试一次,最多等 120 秒。 等满还没通也照常执行——签到本身是幂等的,漏一天补不回来, 而脚本自己有重试,总比直接跳过强。

而且日志里会记下每次都判了什么,下次出问题不用猜:

[wrapper] 等待网络就绪(最多 120 秒)...
[wrapper] 网络探测: ping=True tcp443=True
[wrapper] 网络就绪(ping tieba.baidu.com 通,等了约 0 秒),开始签到。

七、我做过的最蠢的一件事:把任务弄没了

改需求的时候要重新注册任务,而注册计划任务需要管理员权限。 我的终端没有这个权限,可我写的安装脚本是这样的顺序: 

# 旧版本,千万别这么写
if ($existing) {
    Unregister-ScheduledTask -TaskName $TaskName -Confirm:$false   # 先删
}
Register-ScheduledTask -TaskName $TaskName -InputObject $task      # 再建

于是:删除成功了,注册被拒绝 (Register-ScheduledTask : Access is denied.)。 结果是——旧任务没了,新任务也没建上,一个都不剩。

正确的写法是覆盖,而不是先删后建:

Register-ScheduledTask -TaskName $TaskName -InputObject $task -Force -ErrorAction Stop

并且注册失败必须明确抛错、并且说明「原有任务未被改动」, 绝对不能静默地把旧任务留在被删状态。

教训很朴素,但我确实又犯了一遍:破坏性操作不要放在可能失败的操作前面。

顺序反过来,最坏的结果只是「没改成」;顺序错了,最坏的结果是「什么都没了」。

另外,既然注册总要管理员权限,那就别让用户去开管理员终端敲命令—— 给一个双击就自动提权的 .cmd 引导脚本,点一下 UAC 的「是」就完事。 顺带还能在注册完立刻试跑一次,当场证明「SYSTEM 身份下也跑得通」, 而不是等到下次开机才发现不行。

八、几条留给以后的自己

  1. 先分清「环境问题」和「代码问题」。 同一个接口,换个库就通,那不是逻辑错,是环境差异 —— 做兼容层,不要继续挖。
  2. 没有真实账号也能给接口定性。 用「格式合法但内容无效」的凭据打接口,靠错误码的差别推断它走到了哪一步。
  3. 幂等是无人值守的前提。 重复签到返回「已签过」而不是报错,才敢让它在开机、定时、手动各处随便跑。
  4. 「看起来没反应」要按「根本没启动」去查。 计划任务先看「上次运行时间」,它比任何日志都诚实。
  5. 凭据只放在被忽略的文件里。 cookie 等于账号密码,开源前用 git grep --cached 扫一遍暂存内容, 确认邮箱、本机路径、真凭据一个都没进去。

九、尾声

这个项目最有意思的地方,是它让我意识到:很多「接口文档」是别人试出来的,而不是官方给的。 两套签名、两个入口、一组错误码,拼在一起才够还原真实行为。 而我自己写的安装脚本,也因为一个顺序问题,给使用者造成了实实在在的损失。

所以结尾还是那句:工具真正的价值,不在于它顺利跑完的那一次, 而在于它坏掉的时候,你能不能在五分钟内知道原因。 这也是为什么最后我把 --check 做成了一个正经功能: 它不带 cookie 也能跑,把「连通 / 登录态 / 关注列表 / 试签」摊成四步,直接告诉你卡在哪。
